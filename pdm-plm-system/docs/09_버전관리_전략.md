# 09. 버전관리 전략 (Git + 시스템 버전 이력)

## 9.1 Git 브랜치 전략 (GitHub Flow 기반)

```
main (운영 배포 브랜치)
  │
  ├── feature/pdm-part-numbering      ← 기능 개발
  ├── feature/bom-tree-viewer
  ├── feature/approval-workflow
  │
  ├── fix/drawing-upload-bug          ← 버그 수정
  │
  └── release/v1.2.0                  ← 릴리즈 준비
```

### 브랜치 운영 규칙

```bash
# ─── 신규 기능 개발 ───────────────────────────────────────────────
git checkout -b feature/pdm-ecn-management
# 개발 완료 후
git push origin feature/pdm-ecn-management
# GitHub에서 PR 생성 → 코드 리뷰 → main 머지

# ─── 긴급 버그 수정 ───────────────────────────────────────────────
git checkout -b fix/drawing-revision-bug main
git push origin fix/drawing-revision-bug

# ─── 릴리즈 태깅 ─────────────────────────────────────────────────
git tag -a v1.2.0 -m "BOM 트리 뷰어 추가, ECN 워크플로우 개선"
git push origin v1.2.0
```

## 9.2 시맨틱 버전 관리 (SemVer)

```
v{MAJOR}.{MINOR}.{PATCH}

MAJOR: API 하위 호환성이 깨지는 변경 (ex: Firestore 스키마 변경)
MINOR: 하위 호환되는 신기능 추가 (ex: BOM 뷰어 추가)
PATCH: 버그 수정 (ex: Revision 계산 오류 수정)

예시:
v1.0.0 - 최초 운영 배포
v1.1.0 - BOM Where-Used 기능 추가
v1.1.1 - 도면 업로드 100MB 제한 버그 수정
v2.0.0 - PLM 라이프사이클 관리 기능 추가 (스키마 변경)
```

## 9.3 시스템 버전 + 도면 Revision 이중 관리

PDM 시스템 자체의 버전과 도면 Revision은 분리하여 관리합니다.

```
시스템 버전 (개발/배포 버전)    도면 Revision (설계 변경 이력)
─────────────────────────    ─────────────────────────────
v1.0.0 배포                    CH-001 Rev.A 등록
v1.1.0 배포                    CH-001 Rev.B (설계 변경)
                               CH-001 Rev.C (재질 변경)
v1.2.0 배포                    CH-001 Rev.D (치수 수정)
v2.0.0 배포 (PLM 추가)          CH-001 Rev.E (PLM 연계)
```

## 9.4 Firestore 스키마 마이그레이션 관리

Firestore는 스키마리스(Schemaless)이므로 필드 추가/변경 시 마이그레이션 스크립트로 관리합니다.

```javascript
// scripts/migrate_v2_0_0.js
// 마이그레이션: parts 컬렉션에 'lifecycle' 필드 추가 (PLM v2.0.0)

const admin = require('firebase-admin');
admin.initializeApp();
const db = admin.firestore();

async function migrate() {
  console.log('[마이그레이션 v2.0.0] 시작');
  const snapshot = await db.collection('parts').get();

  const batch = db.batch();
  let count = 0;

  snapshot.docs.forEach(doc => {
    const data = doc.data();

    // 신규 필드가 없는 문서만 업데이트
    if (!data.lifecycle) {
      batch.update(doc.ref, {
        lifecycle: {
          phase: 'Design',        // Design | Prototype | Production | End-of-Life
          qualifiedDate: null,
          productionDate: null
        },
        schemaVersion: '2.0.0'
      });
      count++;
    }

    // Firestore 배치 한도 500건 제어
    if (count % 490 === 0) {
      batch.commit();
    }
  });

  await batch.commit();
  console.log(`[마이그레이션 v2.0.0] 완료: ${count}건 업데이트`);
}

migrate().catch(console.error);
```

```bash
# 마이그레이션 실행
GOOGLE_APPLICATION_CREDENTIALS=./serviceAccountKey.json node scripts/migrate_v2_0_0.js
```

## 9.5 환경별 배포 전략

```
개발(dev) ──→ 스테이징(staging) ──→ 운영(production)

환경별 GCP 프로젝트 분리:
- pdm-plm-dev        (개발자 개인 테스트)
- pdm-plm-staging    (통합 테스트, 고객 검수)
- pdm-plm-prod       (실제 운영)
```

```bash
# 환경별 Firebase 프로젝트 설정
firebase use --add
# 각 환경 선택 후 alias 설정: dev, staging, production

# 환경별 배포
firebase use dev
firebase deploy

firebase use production
firebase deploy
```
